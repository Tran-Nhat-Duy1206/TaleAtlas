## Actual source findings and decisions

- Titles have UUIDs, but existing public/admin DTOs omit them. The current full writer preserves unchanged assertions' UUID/source; a changed title gets a new UUID. V5A's UUID-targeted text replacement is a **future row-aware contract**, not a claim that the current writer implements it. No target-ID DTO or adapter was added.
- Descriptions have primary key `(work_id, language)`, not UUIDs. Preserve that natural identity; changing language is deferred, not an invented row-ID/move operation.
- Runtime language grammar is narrower than the database grammar. New input uses current runtime grammar; trusted legacy context retains the existing DB grammar and exact case-sensitive keys. No automatic language/Unicode identity reconciliation.
- The current writer replaces child collections and preserves unchanged exact assertions/source IDs; detached DTOs and latest aggregate citation cannot establish safe merge or per-child history. New rich writes need locked authoritative reads and source/history preservation in V5B.
- Genres have slug/names, no active/retired status. The privileged full writer can create taxonomy rows, but V5 proposals cannot inherit that authority. Approved contract policy is existing-row membership only; retirement semantics remain deferred.
- Descriptions have source attribution, not a stored rights policy. New description text is original-summary-only with an explicit declaration; licenses/permission/public-domain copies are deferred. Neither declaration nor citation proves legal permission.
- Existing field evidence covers Work/edition/cover scalars; no rich-operation storage, child tombstone/history or transactional executor is implemented here.
- The old V2 review is admin/verification guarded, but does not inherit V4's transaction-local persisted principal/session recheck. V5B must provide current persisted authorization under its own locked execution path.

### Identity and duplicate policy

New exact or normalized duplicate title assertions are rejected **within the same Work/language/kind**. Existing alias collisions are grandfathered: preflight never rewrites old data or rejects an unrelated description edit solely for old collisions. A replacement may retain its existing normalized collision key, but cannot introduce a new exact duplicate or move into a different occupied normalized key. Normalization is input duplicate/search assistance, never Work/creator identity, global equivalence or automatic merge.

## Wire contracts and canonical identity

[Pure contracts](../apps/web/src/features/catalog/metadata-operations.ts) export submitMetadataProposalSchema, SubmitMetadataProposal, canonicalMetadataProposalInput and reviewMetadataProposalSchema. The version1 submit envelope is strict, including all nested objects:

```text
version: 1
submitKey: UUID
workId: UUID
baseWorkRevision: integer 1..2147483647
citation: { label, citation, url?, consultedAt? }
operation: one of the explicitly approved type discriminators
```

Title add has value `{title, language, kind}`; replace/remove use titleId. Description add/replace carry `{language,text,rights:{basis:"ORIGINAL_SUMMARY",originalityAcknowledged:true,statement}}`; remove carries language/reason. Genre operations carry slug, and remove carries reason. Unknown authority/owner/role/state/source-ID/slug-rewrite keys, batches and unsupported discriminators are rejected.

- Canonical JSON has fixed whitelist ordering and domain TALEATLAS_METADATA_PROPOSAL_V1, version, Work UUID, base revision, every operation/rights field and every citation field. submitKey is excluded: future delivery uniqueness is **authenticated owner+submitKey**, not title equality. Same key/different canonical input must conflict in future storage; this helper performs no hashing or persistence.
- New-contract UUID strings serialize lowercase. Exact language, case/accent and Unicode composition remain intact; no NFC identity folding. Canonical payload cap60000 UTF8 bytes is separate from the unchanged64KiB streamed HTTP bound. The old six-field canonicalizer and12k budget are untouched.
- Text rejects malformed UTF16, C0/C1 and directional override/isolate controls. Only multiline descriptions/citation/reason/rights statements permit LF/TAB and normalize CRLF/CR to LF; validation precedes trim. Titles/labels/URLs cannot smuggle boundary controls. This is not HTML sanitization: future views must render literal escaped text, never raw HTML.
- Citation labels<=200, citation<=4000, optional existing lexical informational HTTPS URL<=2000, optional offset datetime. No URL fetch/DNS/redirect check, licensed-content permission, consultation proof or public reachability guarantee. Legacy lexical URL behavior remains unchanged.
- Separate strict review intent includes version, suggestion UUID, suggestion revision, Work base revision, bounded reason and APPROVE/REJECT. APPROVE requires literal-true metadata/publication/rights-review acknowledgments; these assert review intent, not current admin identity or verified truth.

## Trusted-context preflight and future integration boundary

[Preflight](../apps/web/src/features/catalog/metadata-operation-safety.ts) reparses unknown input, checks a readonly trusted Work/child/existing-taxonomy snapshot, validates published/current identity/revision (including revision-overflow denial), canonical/ORIGINAL protection, cross-Work scope, natural keys, counts, duplicates and no-ops. Missing and foreign selectors yield the same target denial. It returns a validated proposal or a closed generic denial, never context contents or a mutated Work.

**It does not load, authenticate, authorize, apply, publish or commit anything.** A caller-supplied snapshot is not permission. Future V5B must load/recheck persisted session/admin, published Work and Work-owned row/taxonomy facts under locks; revalidate the entire aggregate/search budget; preserve sibling identities/source history; and atomically commit or roll back every Work/child/evidence/proposal/audit change. An ambiguous write is not automatically retried. No current API is wired to these modules.
