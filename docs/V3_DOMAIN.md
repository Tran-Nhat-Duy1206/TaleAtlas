## Identity, visibility and owner policy

- Entry UUID is private identity, unique `(user_id, work_id)`; stable verified Work UUID remains authoritative. All callers use the authenticated signed session; user/role/owner inputs are forbidden, including admin impersonation. Library reads/writes require an authenticated session, not an administrator role. Better Auth requires email verification for actual sign-in; no new privilege or public-sharing grant.
- Catalog display is projected from current verified titles in the chosen locale, never a stored private copy promoted to the catalog. Published Work metadata is read under a repeatable-read snapshot; hidden/draft/missing Works yield only an unavailable-Work placeholder and the owner's private facts. Catalog titles/slugs/descriptions/editions/covers must not leak through private history snapshots. Library events contain only private input/facts and UUID references, not cached Work metadata.
- Missing catalog identity leads to existing Request a Story, not privately invented public Works. Adding requires PUBLISHED visibility. Hidden owned records remain readable/editable privately, removable and historically preserved; no new Edition selection from an unavailable Work.
- Edition selection uses existing `editions(id,work_id)` uniqueness. Nullable `editionId` + nullable `editionWorkId` composite FK with ON DELETE SET NULL, and a paired/equal-to-session-Work check, enforce Work scope without altering or blocking V1 Edition removal. Removing a catalog Edition clears only its live reference; user progress/history stays. No applied0000–0007 migration or catalog identity/provenance semantics changes.

## Entry lifecycle and removal

Statuses: `WANT_TO_READ`, `READING`, `COMPLETED`, `ON_HOLD`, `DROPPED`. Default add is WANT_TO_READ. Duplicate active add returns the same entry without an additional read or duplicated history. All real changes carry an opaque UUID `mutationKey` and exact `revision`; unchanged idempotent replay is owner/entry/key/canonical-SHA256 bound and never overwrites newer state. Mutation keys also occupy one namespace per owner across entries/commands, with a database unique(owner,key) fence; rebinding an owner's key to another Work conflicts. Changed content reusing a recorded mutation key conflicts. No-op/duplicate-active-add commands do not write history or reserve a fresh key; existing recorded keys still validate scope/hash, and no-op updates must match the current entry revision. All UUID inputs are normalized to lowercase before comparing/hashing PostgreSQL identities. First add needs no revision; restoring an archived entry requires its exact revision.

Removal requires explicit `confirmRemoval: true`. It archives the entry, closes any unfinished session as ABANDONED (not completed), and keeps private notes/ratings/history. Removed entries do not appear in saved-Work pages. Re-add restores the same entry/history to WANT_TO_READ; it does not falsely resume or complete a read. UI must explicitly explain retention, not call this permanent deletion. Account deletion CASCADE-erases all V3 private entries, sessions, events and ratings/notes; no detached personal reading audit survives in application tables. External backups/operational logs are a separately documented hosted limit, not claimed erased.

## Explicit sessions, progress and dates

Session states `ACTIVE`, `PAUSED`, `COMPLETED`, `ABANDONED`; immutable sequence per entry, kind `FIRST_READ` or `REREAD` based on whether a previous completed read exists. One unfinished ACTIVE/PAUSED session per entry, SQL partial unique index. Terminal sessions never reopen. New reading after a prior completed read needs explicit reread acknowledgment/action; preserves previous completion/progress. Before any completed read, another attempt is still FIRST_READ and distinguishable by sequence.

- READING starts a first read when none exists, or resumes the same unfinished read. ON_HOLD/WANT_TO_READ pauses an unfinished read. DROPPED abandons it. COMPLETED completes the unfinished read; explicitly marking previously read without an open session creates a completed personal record, not an invented historical date. Already completed is a no-op. Explicit START_READ/START_REREAD/RESUME/COMPLETE session actions expose this lifecycle.
- Entry revision serializes all session/progress/notes/favorite mutations under an owned entry row lock. Session has its own positive revision for stored history, but callers fence by the parent entry revision to prevent cross-feature lost updates. Compound entry/session/event mutations are atomic.
- Progress belongs to an unfinished session: optional integer chapterNumber0–1,000,000, chapterLabel<=200; volumeNumber0–100,000 or volumeLabel<=200; optional Edition, private personalChapterTotal1–1,000,000, progressNotes<=2000. Null explicitly clears optional values; unknown fields rejected. No global totals, percentage, schedule, finished date or reading duration is inferred. Personal totals are explicitly private and never treated as verified catalog facts.
- `startedAt`/`completedAt`/`closedAt`/`lastActivityAt` are timestamps of explicit personal commands, labeled as recorded/marked activity, not proof of when a book was actually read. Optional exact Gregorian `startedOn`/`finishedOn` come from the user; nullable, validated chronology when both supplied. Last activity only changes on explicit reading/session/progress actions, not favorites or notes. No elapsed reading time computed from timestamps.
- Progress snapshots are appended per change; previous sessions and their final progress remain distinguishable and owner-only. Session notes<=2000 may be supplied at start/completion. Closed-session progress cannot silently be overwritten.

## Rating, notes, bounds and query policy

Private rating scale:1–5 stars in half-star increments, stored `ratingHalfStars` integer2–10 or NULL. Private entry notes plain text<=4000, session/progress notes<=2000; editable entry notes and clearable rating, no HTML rendering/public reviews/community aggregate/popularity. No shared library visibility switch or event-to-public-feed adapter.

Bounded domain:20,000 entries per owner (including archived);1,000 sessions and10,000 retained mutation events per entry. Limits reject before writing with explicit safe errors; no silent pruning or deletion of original completion/progress. Event JSON object<=32KiB, no catalog metadata. Progress event count is bounded by parent events. Queries return at most50 entries/events/sessions per page, validated page<=400 with fixed50-entry pages, or exact numeric beforeRevision/beforeSequence cursor for owner-only timelines; stable order with UUID tie-breakers. Sorting by saved/update activity/title/rating is private; filters status/favorite and validated locale. Hidden items use an unavailable label, not hidden titles for search/sort. Rate budget reuses authenticated atomic30 mutations/minute without double charging or resetting unrelated rows; HTTP JSON streaming bound<=64KiB, strict origin/CSRF, no-store and safe errors.

This policy is an implementation decision, not a claim of delivered V3 UX. Actual milestone results and failures are recorded in the [V3 validation ledger](V3_VALIDATION.md) before acceptance.
